# 第十三周学习说明：事务、Todo 操作日志和数据一致性

第十三周的目标是让 Todo API 从“保存当前状态”升级成“记录历史过程”。

前面项目已经能做到：

```text
创建 Todo
修改 Todo
完成 / 取消完成 Todo
软删除 Todo
恢复 Todo
统一响应结构
用户数据隔离
```

这一周继续往真实后端项目靠近：我们新增 Todo 操作日志。

最核心的一句话：

```text
业务系统不只关心现在是什么状态，也关心这个状态是怎么一步步变成现在这样的。
```

## 第一步：为什么需要操作日志？

前几周我们的 Todo 表能告诉你：

```text
这个 Todo 当前标题是什么
是否完成
是否删除
什么时候创建
什么时候更新
```

但是它不能告诉你：

```text
这个 Todo 曾经被修改过几次？
什么时候完成的？
什么时候删除的？
谁操作的？
恢复之前发生了什么？
```

所以我们新增一张日志表。

以后一个 Todo 可能有多条日志：

```text
Todo 1
  -> CREATED
  -> UPDATED
  -> COMPLETED
  -> DELETED
  -> RESTORED
```

这就像给 Todo 加了一条“时间线”。

## 第二步：新增 V5 migration

文件：

```text
src/main/resources/db/migration/V5__create_todo_action_logs_table.sql
```

核心表结构：

```sql
CREATE TABLE todo_action_logs (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    todo_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    action VARCHAR(50) NOT NULL,
    description VARCHAR(255) NOT NULL,
    created_at TIMESTAMP NOT NULL,
    CONSTRAINT fk_todo_action_logs_todo FOREIGN KEY (todo_id) REFERENCES todos(id),
    CONSTRAINT fk_todo_action_logs_user FOREIGN KEY (user_id) REFERENCES users(id)
);
```

字段解释：

| 字段 | 含义 |
|---|---|
| `id` | 日志自己的主键 |
| `todo_id` | 这条日志属于哪个 Todo |
| `user_id` | 谁执行了这个操作 |
| `action` | 操作类型，例如 `CREATED`、`DELETED` |
| `description` | 给人看的描述，例如 `创建 Todo` |
| `created_at` | 日志产生时间 |

为什么要单独建表？

因为一个 Todo 会有多条日志。

如果放在 `todos` 表里，就只能保存一个当前值，不适合保存历史列表。

## 第三步：为什么新增索引？

migration 里还有：

```sql
CREATE INDEX idx_todo_action_logs_todo_id_created_at
    ON todo_action_logs (todo_id, created_at);
```

因为我们最常见的查询是：

```text
查询某个 Todo 的所有日志，并按时间排序
```

也就是：

```sql
WHERE todo_id = ?
ORDER BY created_at ASC
```

索引可以让这种查询更快。

另一个索引：

```sql
CREATE INDEX idx_todo_action_logs_user_id
    ON todo_action_logs (user_id);
```

为以后扩展“查询某个用户最近所有操作”做准备。

## 第四步：TodoAction 枚举是什么？

文件：

```text
src/main/java/com/zading/todoapi/model/TodoAction.java
```

内容：

```java
public enum TodoAction {
    CREATED,
    UPDATED,
    COMPLETED,
    UNCOMPLETED,
    DELETED,
    RESTORED
}
```

为什么不用普通字符串？

比如：

```java
"CREATE"
"created"
"CREATED"
"create_todo"
```

如果用字符串，写错了编译器也不知道。

用枚举后，动作类型被限制在固定范围内。

如果你写：

```java
TodoAction.CREATEED
```

编译器会直接报错。

这就是类型安全。

## 第五步：TodoActionLog Entity 怎么理解？

文件：

```text
src/main/java/com/zading/todoapi/model/TodoActionLog.java
```

核心代码：

```java
@Entity
@Table(name = "todo_action_logs")
public class TodoActionLog {
}
```

表示：

```text
这个 Java 类对应数据库里的 todo_action_logs 表。
```

### 1. 它和 Todo 是什么关系？

代码：

```java
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "todo_id", nullable = false)
private Todo todo;
```

含义：

```text
多条日志属于同一个 Todo。
```

所以是：

```text
TodoActionLog 多 -> 一 Todo
```

也就是 `ManyToOne`。

### 2. 它和 AppUser 是什么关系？

代码：

```java
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "user_id", nullable = false)
private AppUser user;
```

含义：

```text
多条日志可以由同一个用户产生。
```

所以也是 `ManyToOne`。

### 3. `FetchType.LAZY` 是什么？

`LAZY` 可以先简单理解为：

```text
查询日志时，不立刻把关联的 Todo 和 User 全部查出来。
```

这样可以减少不必要的数据库查询。

在这个接口里，我们返回日志时只需要：

```text
id
action
description
createdAt
```

不需要返回完整 Todo 或完整 User。

所以 `LAZY` 更合适。

## 第六步：`@PrePersist` 是什么？

`TodoActionLog` 里有：

```java
@PrePersist
void onCreate() {
    this.createdAt = LocalDateTime.now();
}
```

意思是：

```text
在 JPA 第一次保存这个对象之前，自动执行这个方法。
```

所以创建日志时，不需要每次手动写：

```java
log.setCreatedAt(LocalDateTime.now());
```

Entity 会自己补上创建时间。

## 第七步：TodoActionLogRepository 做了什么？

文件：

```text
src/main/java/com/zading/todoapi/repository/TodoActionLogRepository.java
```

代码：

```java
List<TodoActionLog> findByTodoIdAndUserIdOrderByCreatedAtAscIdAsc(Long todoId, Long userId);
```

这是 Spring Data JPA 的方法名查询。

拆开看：

```text
findBy
  TodoId
  And
  UserId
OrderBy
  CreatedAt Asc
  Id Asc
```

意思是：

```text
查询某个 Todo、某个用户下面的日志，并按 createdAt、id 正序排列。
```

为什么加 `UserId`？

为了用户隔离。

用户 B 不能查到用户 A 的 Todo 日志。

为什么排序时还加 `IdAsc`？

因为多条日志可能在很短时间内创建，`createdAt` 非常接近。

再加一个 `id` 排序，可以让结果顺序更稳定。

## 第八步：TodoActionLogResponse 为什么需要？

文件：

```text
src/main/java/com/zading/todoapi/dto/TodoActionLogResponse.java
```

它只返回：

```java
private Long id;
private TodoAction action;
private String description;
private LocalDateTime createdAt;
```

为什么不直接返回 Entity？

因为 Entity 里面有：

```java
private Todo todo;
private AppUser user;
```

如果直接返回 Entity，可能会把不该给前端的数据也暴露出去。

比如 User 里有：

```java
passwordHash
```

虽然不一定真的会序列化出来，但工程上不应该冒这个风险。

所以接口返回 DTO。

这就是：

```text
数据库模型和接口模型分离。
```

## 第九步：什么是事务？

事务最简单的理解：

```text
一组数据库操作，要么全部成功，要么全部失败。
```

本周的典型场景：

```text
删除 Todo
  1. 把 todos.deleted 改成 true
  2. 往 todo_action_logs 插入一条 DELETED 日志
```

如果第 1 步成功，第 2 步失败，会怎样？

数据库就会变成：

```text
Todo 已经被删除
但是没有删除日志
```

这就是数据不一致。

所以我们希望：

```text
要么 Todo 删除成功，并且日志也写成功
要么日志写失败时，Todo 删除也回滚
```

这就是事务要解决的问题。

## 第十步：为什么 Service 层加 `@Transactional`？

文件：

```text
src/main/java/com/zading/todoapi/service/TodoService.java
```

这周给写操作加了：

```java
@Transactional
```

例如：

```java
@Transactional
public void deleteTodo(Long userId, Long id) {
    Todo todo = getTodo(userId, id);
    AppUser user = todo.getUser();
    todo.setDeleted(true);
    todo.setDeletedAt(LocalDateTime.now());

    Todo savedTodo = todoRepository.save(todo);
    addActionLog(savedTodo, user, TodoAction.DELETED, "删除 Todo");
}
```

这个方法里有两类数据库操作：

```text
更新 todos
插入 todo_action_logs
```

加了 `@Transactional` 后，它们属于同一个事务。

如果中间抛异常，整个方法内已经执行的数据库修改会回滚。

为什么放 Service，不放 Controller？

因为事务通常围绕业务动作。

Controller 负责 HTTP。

Service 负责业务流程。

所以事务边界放在 Service 更合理。

## 第十一步：读操作为什么是 `readOnly = true`？

代码：

```java
@Transactional(readOnly = true)
public List<TodoActionLog> getTodoLogs(Long userId, Long id) {
}
```

`readOnly = true` 表示：

```text
这个事务只读，不打算修改数据。
```

它的价值：

```text
1. 表达代码意图
2. 让框架和数据库有机会做读优化
3. 避免读方法里误写数据
```

学习阶段先记住：

```text
写操作：@Transactional
读操作：@Transactional(readOnly = true)
```

## 第十二步：创建 Todo 时怎么写日志？

代码逻辑：

```java
Todo savedTodo = todoRepository.save(todo);
addActionLog(savedTodo, user, TodoAction.CREATED, "创建 Todo");
return savedTodo;
```

为什么先保存 Todo，再写日志？

因为日志需要关联：

```text
todo_id
```

新建 Todo 在保存前还没有数据库 id。

保存后：

```java
savedTodo.getId()
```

才有值。

所以顺序必须是：

```text
先保存 Todo
再保存日志
```

## 第十三步：修改 Todo 时为什么可能写多条日志？

`updateTodo` 可能收到：

```json
{
  "title": "新标题",
  "completed": true
}
```

这其实包含两个业务动作：

```text
修改内容
完成 Todo
```

所以代码里区分：

```java
boolean updatedFields = false;
TodoAction completedAction = null;
```

如果修改了标题、优先级或截止日期：

```java
updatedFields = true;
```

最后写：

```java
addActionLog(savedTodo, user, TodoAction.UPDATED, "修改 Todo");
```

如果完成状态发生变化：

```java
completedAction = completed ? TodoAction.COMPLETED : TodoAction.UNCOMPLETED;
```

最后写：

```java
addActionLog(savedTodo, user, completedAction, getCompletedDescription(completedAction));
```

这样日志会更贴近真实业务。

## 第十四步：切换完成状态怎么写日志？

代码：

```java
boolean nextCompleted = !todo.isCompleted();
applyCompleted(todo, nextCompleted);
TodoAction action = nextCompleted ? TodoAction.COMPLETED : TodoAction.UNCOMPLETED;
addActionLog(savedTodo, user, action, getCompletedDescription(action));
```

如果原来是未完成：

```text
nextCompleted = true
日志 = COMPLETED / 完成 Todo
```

如果原来是完成：

```text
nextCompleted = false
日志 = UNCOMPLETED / 取消完成 Todo
```

这和第十一周的 `completedAt` 逻辑配合：

```text
完成：写 completedAt
取消完成：清空 completedAt
```

## 第十五步：删除和恢复怎么写日志？

删除：

```java
todo.setDeleted(true);
todo.setDeletedAt(LocalDateTime.now());
addActionLog(savedTodo, user, TodoAction.DELETED, "删除 Todo");
```

恢复：

```java
todo.setDeleted(false);
todo.setDeletedAt(null);
addActionLog(savedTodo, user, TodoAction.RESTORED, "恢复 Todo");
```

注意：

```text
删除依然是软删除，不是物理删除。
```

日志表里会保留这次删除动作。

以后做“回收站”或“审计记录”时，这些日志就有用了。

## 第十七步：为什么先检查 Todo 是否属于当前用户？

Service 里：

```java
todoRepository.findByIdAndUserId(id, userId)
        .orElseThrow(() -> new TodoNotFoundException(id));
```

这一步不是为了拿日志，而是为了确认：

```text
这个 Todo 存在，并且属于当前用户。
```

如果用户 B 查用户 A 的日志：

```text
findByIdAndUserId(userATodoId, userBId)
```

查不到。

最终返回：

```json
{
  "success": false,
  "code": "TODO_NOT_FOUND",
  "message": "Todo 不存在，id = 1"
}
```

这里我们故意返回“Todo 不存在”，而不是“无权限”。

原因是：

```text
不向用户 B 暴露用户 A 的 Todo 是否真实存在。
```

这是常见的安全设计。

## 第十八步：为什么测试清理顺序要改？

文件：

```text
src/test/java/com/zading/todoapi/support/AbstractApiTest.java
```

现在清理顺序：

```java
todoActionLogRepository.deleteAll();
todoRepository.deleteAll();
userRepository.deleteAll();
```

为什么日志要先删？

因为日志表有外键：

```text
todo_action_logs.todo_id -> todos.id
todo_action_logs.user_id -> users.id
```

如果先删 Todo 或 User，数据库会发现：

```text
还有日志引用它们
```

然后拒绝删除。

所以必须先删子表，再删父表。

简单记：

```text
有外键依赖时，删除顺序通常是：先子表，后父表。
```

## 本周你需要真正掌握的点

### 1. 一次业务操作可能影响多张表

例如删除 Todo：

```text
更新 todos
插入 todo_action_logs
```

这不是两个独立动作，而是一个完整业务动作。

### 2. 事务保证数据一致性

`@Transactional` 可以让一组数据库操作：

```text
要么一起成功
要么一起失败
```

### 3. 日志表是历史记录，不是当前状态

`todos` 表保存当前状态。

`todo_action_logs` 表保存发生过的动作。

这两种数据职责不同。

### 4. DTO 保护接口边界

日志 Entity 里有关联的 `Todo` 和 `AppUser`。

接口不应该直接返回 Entity，而应该返回 `TodoActionLogResponse`。

### 5. 用户隔离不只影响 Todo，也影响日志

只要数据属于用户，就要考虑用户隔离。

Todo 日志也不能跨用户访问。

## 本周复盘问题和参考答案

### 1. 什么是事务？

事务是一组数据库操作的执行边界。事务内的操作要么全部成功，要么遇到异常后全部回滚。

### 2. 为什么 Todo 操作日志需要事务？

因为一个业务动作会同时修改 Todo 和写入日志。如果 Todo 修改成功但日志写入失败，数据就不完整。

### 3. 为什么 `@Transactional` 放在 Service 层？

因为 Service 层表达业务流程。事务通常围绕完整业务动作，而不是围绕 HTTP 请求或单个数据库调用。

### 4. `@Transactional(readOnly = true)` 有什么作用？

它表示这个方法只读，不修改数据。它能表达代码意图，也可能帮助框架做读优化。

### 5. 为什么操作类型用 enum？

enum 可以限制取值范围，避免字符串拼写错误，让代码更安全。

### 6. 为什么日志表要有 `todo_id`？

因为每条日志都属于某一个 Todo。查询某个 Todo 的历史时，需要用 `todo_id` 过滤。

### 7. 为什么日志表还要有 `user_id`？

因为需要知道谁执行了操作，也需要做用户数据隔离。

### 8. `ManyToOne` 表示什么？

表示多条当前 Entity 记录关联到一条目标 Entity。例如多条 TodoActionLog 属于同一个 Todo。

### 9. 为什么查询日志时不直接返回 `TodoActionLog` Entity？

因为 Entity 里可能有关联对象和敏感字段。DTO 可以控制接口返回哪些字段，保护接口边界。

### 10. 为什么测试清理时要先删除日志？

因为日志表有外键引用 Todo 和 User。如果先删除 Todo 或 User，会违反外键约束。

### 11. 为什么用户 B 查询用户 A 的日志返回 404？

为了不暴露用户 A 的 Todo 是否存在。对用户 B 来说，这个资源就应该像不存在一样。

### 12. 为什么日志排序要用 `createdAt` 和 `id`？

`createdAt` 表示时间顺序；`id` 用来在时间非常接近时保证顺序稳定。

### 13. `addActionLog` 为什么抽成私有方法？

因为创建日志的代码会在多个业务方法里重复出现。抽成私有方法可以减少重复，让 Service 更清晰。

### 14. 创建 Todo 时为什么先保存 Todo，再保存日志？

因为新 Todo 保存前还没有数据库 id。日志需要关联 `todo_id`，所以必须先保存 Todo。

### 15. 本周最重要的工程化思想是什么？

业务动作要有完整性。只改当前状态是不够的，真实系统还要考虑历史记录、审计、用户隔离和数据一致性。
