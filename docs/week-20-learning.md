# 第 20 周学习说明：文件上传、下载和 Todo 附件管理

第 20 周的目标是：给 Todo 增加附件能力。

真实业务里经常会遇到：

```text
头像上传
图片上传
合同附件
报表下载
Excel 导入
文件预览
```

所以文件上传 / 下载是后端开发里非常常见的能力。

这一周我们先不接云存储，也不引入 Docker、MinIO、S3 这些外部工具，而是用本地文件系统实现一套可运行、可测试、可理解的附件模块。

一句话：

```text
第 20 周学的是：如何让接口接收文件、保存文件、记录附件元信息，并安全地下载和删除文件。
```

## 第一天：文件上传流程是什么？

一个文件上传请求，大致链路是：

```text
前端选择文件
  -> 使用 multipart/form-data 提交
  -> 后端用 MultipartFile 接收
  -> 校验文件
  -> 保存真实文件到磁盘
  -> 保存附件元信息到数据库
  -> 返回附件信息
```

这里有两个东西要分清楚。

第一，真实文件内容：

```text
图片字节
PDF 字节
文本内容
Excel 内容
```

第二，附件元信息：

```text
原始文件名
存储文件名
Content-Type
文件大小
存储路径
所属 Todo
所属用户
上传时间
```

这周的设计是：

```text
真实文件 -> 存本地 uploads 目录
附件元信息 -> 存数据库 todo_attachments 表
```

## 第二天：为什么数据库不直接存文件内容？

数据库可以存文件内容，比如用 BLOB 字段。

但大多数业务系统更常见的做法是：

```text
文件内容放文件系统或对象存储
数据库只保存文件元信息和访问路径
```

原因：

```text
数据库更适合存结构化数据
大文件会让数据库备份和迁移变重
文件系统 / 对象存储更适合保存大量二进制文件
下载文件时直接读取文件流更自然
```

所以本项目新增了：

```text
todo_attachments 表
uploads/ 文件目录
```

这也是后续接 S3、MinIO、阿里云 OSS 时的基础思想。

## 第三天：附件表怎么设计？

文件：

```text
src/main/resources/db/migration/V6__create_todo_attachments_table.sql
```

核心字段：

```sql
CREATE TABLE todo_attachments (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    todo_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    original_filename VARCHAR(255) NOT NULL,
    stored_filename VARCHAR(255) NOT NULL,
    content_type VARCHAR(100) NOT NULL,
    file_size BIGINT NOT NULL,
    storage_path VARCHAR(500) NOT NULL UNIQUE,
    created_at TIMESTAMP NOT NULL
);
```

字段说明：

| 字段 | 说明 |
|---|---|
| `todo_id` | 附件属于哪个 Todo |
| `user_id` | 附件属于哪个用户 |
| `original_filename` | 用户上传时的原始文件名 |
| `stored_filename` | 后端生成的真实存储文件名 |
| `content_type` | 文件类型，例如 `text/plain` |
| `file_size` | 文件大小，单位字节 |
| `storage_path` | 文件在本地存储中的相对路径 |
| `created_at` | 上传时间 |

为什么同时存 `todo_id` 和 `user_id`？

因为权限校验更直接。

例如查询附件时可以明确表达：

```text
查 todoId = 10 且 userId = 当前用户 的附件
```

这能避免用户访问别人 Todo 的附件。

## 第四天：为什么要有 originalFilename 和 storedFilename？

`originalFilename` 是用户上传时的文件名：

```text
合同.pdf
头像.png
note.txt
```

它适合展示给用户。

`storedFilename` 是后端生成的文件名：

```text
3f9a0b27-55fb-4b3e-bc20-e43e65c8f1c7.pdf
```

它适合真实保存到磁盘。

为什么不直接用用户上传的文件名保存？

因为用户上传的文件名可能：

```text
重复
包含特殊字符
包含路径攻击
过长
不适合不同操作系统
```

所以本项目使用 UUID 生成真实文件名：

```java
UUID.randomUUID() + getExtension(originalFilename)
```

这样可以减少重名风险。

## 第九天：Service 上传逻辑做了什么？

文件：

```text
src/main/java/com/zading/todoapi/service/TodoAttachmentService.java
```

上传主流程：

```java
Todo todo = getVisibleTodo(userId, todoId);
validateFile(file);

Path rootLocation = getRootLocation();
String originalFilename = normalizeOriginalFilename(file.getOriginalFilename());
String storedFilename = generateStoredFilename(originalFilename);
String storagePath = "todo-attachments/" + userId + "/" + todoId + "/" + storedFilename;
Path targetPath = resolveStoragePath(rootLocation, storagePath);

Files.createDirectories(targetPath.getParent());
file.transferTo(targetPath);

// 设置元信息
return todoAttachmentRepository.save(attachment);
```

这段代码做了几件重要的事：

```text
确认 Todo 属于当前用户
检查文件不能为空
检查文件大小不能超过限制
清理原始文件名
生成安全的存储文件名
创建目录
保存文件到磁盘
保存元信息到数据库
```

## 第十天：为什么要先 getVisibleTodo？

代码：

```java
private Todo getVisibleTodo(Long userId, Long todoId) {
    return todoRepository.findByIdAndUserIdAndDeletedFalse(todoId, userId)
            .orElseThrow(() -> new TodoNotFoundException(todoId));
}
```

它的含义是：

```text
只能给当前用户自己的、未删除的 Todo 上传附件。
```

如果 Todo 不存在，或者属于别人，或者已经软删除，就返回：

```text
TODO_NOT_FOUND
```

这是权限隔离的一种常见写法：

```text
不要告诉用户“这个资源存在但不属于你”
直接当作不存在
```

## 第十一天：为什么要检查文件名安全？

代码：

```java
String cleanedFilename = StringUtils.cleanPath(originalFilename);

if (cleanedFilename.contains("..")) {
    throw new BusinessException(ErrorCode.BAD_REQUEST, "附件文件名不安全");
}
```

为什么要防 `..`？

因为 `..` 代表上级目录。

如果不处理，恶意文件名可能尝试写到上传目录之外：

```text
../../some-file
```

所以文件路径必须做安全处理。

本项目还有第二层保护：

```java
Path resolvedPath = rootLocation.resolve(storagePath).normalize();

if (!resolvedPath.startsWith(rootLocation)) {
    throw new BusinessException(ErrorCode.BAD_REQUEST, "附件路径不安全");
}
```

这能确保最终路径仍然在上传根目录下。

## 第十二天：下载接口怎么实现？

接口：

```java
@GetMapping("/{attachmentId}/download")
public ResponseEntity<Resource> downloadAttachment(...) {
}
```

下载时返回的不是统一 `ApiResponse`。

原因是：

```text
下载接口要返回文件字节流，不是 JSON。
```

核心响应头：

```java
.contentType(parseMediaType(download.contentType()))
.contentLength(download.fileSize())
.header(HttpHeaders.CONTENT_DISPOSITION, contentDisposition.toString())
.body(download.resource());
```

`Content-Type` 告诉浏览器：

```text
这是什么类型的文件。
```

`Content-Disposition: attachment` 告诉浏览器：

```text
把它当附件下载。
```

`Resource` 是 Spring 对“资源”的抽象。

它可以代表：

```text

```

这里用它包装本地文件，让 Spring MVC 帮我们把文件内容写到 HTTP 响应里。

## 第十四天：删除附件做了什么？

删除接口：

```http
DELETE /api/todos/{todoId}/attachments/{attachmentId}
```

Service 逻辑：

```java
TodoAttachment attachment = getAttachment(userId, todoId, attachmentId);
Path filePath = resolveStoragePath(getRootLocation(), attachment.getStoragePath());
```

它做两件事：

```text

```

本周先做简单版本：

```text
在一个 Service 方法里连续处理数据库和文件。
```

真实生产项目可能会用：

```text
补偿任务
异步清理
对象存储生命周期规则
```


## 本周复盘问题和参考答案

### 1. 什么是 `multipart/form-data`？

它是一种 HTTP 表单提交格式，适合上传文件。

普通 JSON 请求适合传结构化文本数据，`multipart/form-data` 适合同时传字段和文件。

### 2. `MultipartFile` 是什么？

`MultipartFile` 是 Spring MVC 对上传文件的封装。

它可以获取文件名、文件大小、Content-Type，并把文件保存到目标位置。

### 3. 为什么数据库不直接存文件内容？

因为数据库更适合存结构化数据。

文件内容通常更适合放文件系统或对象存储，数据库只保存元信息和路径。

### 4. 为什么要保存 `originalFilename` 和 `storedFilename`？

`originalFilename` 用于展示给用户。

`storedFilename` 用于真实保存，通常由后端生成，避免重名和路径安全问题。

### 5. 为什么不能直接相信用户上传的文件名？

用户上传的文件名可能重复、包含特殊字符，甚至包含 `../` 这类路径攻击内容。

所以后端必须清理文件名，并生成自己的存储文件名。

### 6. 下载接口为什么不返回 `ApiResponse`？

因为下载接口返回的是文件字节流，不是 JSON。

如果包装成 `ApiResponse`，就不是真正的文件下载了。

### 7. `Content-Disposition: attachment` 有什么作用？

它告诉浏览器把响应当作附件下载。

### 8. 删除附件为什么会有一致性问题？

因为删除附件涉及两个系统：

```text
数据库
文件系统
```

只要跨两个系统，就可能出现一个成功、另一个失败的问题。

### 9. 为什么测试要清理文件目录？

因为附件测试不只写数据库，还会写磁盘文件。

为了让每次测试独立、可重复，需要清理测试上传目录。

### 10. 本地存储和云存储有什么区别？

本地存储是把文件放在应用所在机器的目录里。

云存储是把文件放到专门的对象存储服务里，例如 S3、MinIO、OSS。

本地存储适合学习和小型部署，云存储更适合生产环境和多实例服务。

## 代码精读补充

### 1. 上传接口中的 `MultipartFile`

```java
@PostMapping(consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
public ApiResponse<TodoAttachmentResponse> upload(
        @PathVariable Long todoId,
        @RequestPart("file") MultipartFile file
) {
    return ApiResponse.created(service.upload(todoId, file));
}
```

`multipart/form-data` 不是 JSON，而是由多个 part 组成的请求体；`@RequestPart("file")` 找到名为 `file` 的文件部分，Spring 将它包装为 `MultipartFile`。Controller 只负责接收，大小、路径和用户权限由 Service 处理。

### 2. 上传业务的两个保存动作

```text
校验当前用户能访问 Todo
  -> 校验文件非空、大小和文件名
  -> 生成安全的 storedFilename
  -> 保存文件到 uploads
  -> 保存 TodoAttachment 元数据
```

文件系统和数据库不是同一个事务，所以代码必须明确失败补偿策略：数据库保存失败时删除刚写入的文件，文件写入失败时不能保存元数据。

### 3. 为什么下载返回文件流

下载接口返回 `Resource` 和 `Content-Disposition: attachment`，浏览器才能把响应当成文件下载。它不是普通 JSON，所以不适合再包一层 `ApiResponse`。
