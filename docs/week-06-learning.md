# 第六周学习说明：Profile + Flyway + DTO 分层

第六周的目标是把项目继续往真实后端工程推进。

第五周结束时，项目已经能做到：

```text
HTTP 请求
  -> Controller
  -> Service
  -> JpaRepository
  -> 数据库
```

第六周要解决三个更工程化的问题：

```text
1. 数据库表结构如何管理？
2. Entity 是否应该直接返回给前端？
3. 不同环境的配置如何长期维护？
```

本周完成后，当前项目变成：

```text
HTTP 请求
  -> Controller
  -> Service
  -> Repository
  -> 数据库

数据库结构
  -> 由 Flyway migration 管理

接口响应
  -> 返回 TodoResponse DTO
  -> 不直接暴露 Todo Entity
```

## 本周最终改动总览

| 改动 | 文件 | 目的 |

| 添加 Flyway 依赖 | `pom.xml` | 管理数据库结构版本 |

## 第一步：为什么引入 Flyway？

第五周项目里有这样的配置：

```properties
spring.jpa.hibernate.ddl-auto=update
```

它的意思是：让 Hibernate 根据 Entity 自动更新数据库表。

学习早期这样很方便，但真实项目里有问题：

- 表结构变化没有清晰历史。
- 不容易知道某次上线改了哪些字段。
- 团队协作时，每个人数据库状态可能不一致。
- 自动改表不够可控，生产环境风险更高。

所以第六周改成：

```properties
spring.jpa.hibernate.ddl-auto=validate
```

含义变成：

```text
Flyway 负责建表和改表
JPA 负责校验 Entity 和数据库表是否匹配
```

这是一条很重要的后端工程边界。

## 第二步：添加 Flyway 依赖

文件：

```text
pom.xml
```

新增：

```xml
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-core</artifactId>
</dependency>

<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-database-postgresql</artifactId>
</dependency>
```

为什么要两个？

- `flyway-core` 是 Flyway 核心能力。
- `flyway-database-postgresql` 是 Flyway 对 PostgreSQL 的数据库支持。

你现在默认用 H2，未来启用 PostgreSQL profile 时也能直接使用 Flyway。

## 第三步：新增 V1 迁移脚本

文件：

```text
src/main/resources/db/migration/V1__create_todos_table.sql
```

内容：

```sql
CREATE TABLE todos (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title VARCHAR(255) NOT NULL,
    completed BOOLEAN NOT NULL DEFAULT FALSE,
    created_at TIMESTAMP NOT NULL,
    updated_at TIMESTAMP NOT NULL
);
```

Flyway 文件名有规则：

```text
V版本号__说明.sql
```

注意中间是两个下划线：

```text
V1__create_todos_table.sql
```

为什么要这样命名？

Flyway 会根据版本号顺序执行脚本：

```text
V1 -> V2 -> V3 -> ...
```

以后如果要新增字段，可以继续加：

```text
V2__add_priority_to_todos.sql
```

不要回头改已经执行过的 V1。这个习惯很重要。

## 第四步：配置 Flyway 和 ddl-auto=validate

默认配置：

```text
src/main/resources/application.properties
```

关键配置：

```properties
spring.jpa.hibernate.ddl-auto=validate
spring.flyway.enabled=true
spring.flyway.locations=classpath:db/migration
```

为什么这么做：

- `validate`：JPA 启动时检查 Entity 和数据库表是否匹配。
- `spring.flyway.enabled=true`：启动 Flyway。
- `locations`：告诉 Flyway 去哪里找 SQL 脚本。

启动顺序大致是：

```text
Spring Boot 启动
  -> 连接数据库
  -> Flyway 执行 migration
  -> Hibernate 校验 Entity 和表结构
  -> 应用启动完成
```

如果 migration 写错，项目会启动失败。

如果 Entity 和表结构不匹配，项目也会启动失败。

这听起来严格，但这是好事：问题越早暴露，越容易修。

## 第五步：为什么默认数据库文件改成 todo-db-v2？

默认配置里现在是：

```properties
spring.datasource.url=jdbc:h2:file:./data/todo-db-v2;MODE=PostgreSQL
```

为什么不是原来的 `todo-db`？

因为旧数据库可能是第五周由 Hibernate 自动建的，没有 Flyway 的版本记录。

第六周开始，数据库结构由 Flyway 接管。为了避免旧表和新迁移历史冲突，我们换了一个新的 H2 文件：

```text
data/todo-db-v2
```

这不会删除旧数据，只是默认使用新的学习数据库。

## 第六步：给 Todo 增加 createdAt / updatedAt

文件：

```text
src/main/java/com/zading/todoapi/model/Todo.java
```

新增字段：

```java
private LocalDateTime createdAt;

private LocalDateTime updatedAt;
```

为什么要加时间字段？

真实业务里几乎所有核心数据都需要知道：

- 什么时候创建的？
- 什么时候最后修改的？

这类字段常叫审计字段。

## 第七步：用 @PrePersist 和 @PreUpdate 自动维护时间

代码：

```java
@PrePersist
void onCreate() {
    LocalDateTime now = LocalDateTime.now();
    this.createdAt = now;
    this.updatedAt = now;
}

@PreUpdate
void onUpdate() {
    this.updatedAt = LocalDateTime.now();
}
```

含义：

- `@PrePersist`：第一次保存到数据库之前执行。
- `@PreUpdate`：更新数据库之前执行。

为什么不在 Service 里手动写？

因为创建时间、更新时间是 Entity 的生命周期逻辑。放在 Entity 里更集中，不容易漏。

这一步你可以这样理解：

```text
只要 Todo 被创建或更新，它自己知道如何维护时间字段。
```

## 第八步：为什么 Entity 不直接返回给前端？

第五周 Controller 直接返回：

```java
public Todo getTodo(@PathVariable Long id)
```

第六周改成：

```java
public TodoResponse getTodo(@PathVariable Long id)
```

原因是：

```text
Entity 是数据库模型
DTO 是接口模型
```

数据库模型经常会变化，比如以后可能增加：

```java
private String internalNote;
private boolean deleted;
private Long ownerId;
```

这些字段不一定应该返回给前端。

如果 Controller 直接返回 Entity，数据库字段变化就会影响 API 响应。

所以我们新增：

```text
TodoResponse
```

让 API 返回什么变得可控。

## 第九步：新增 TodoResponse

文件：

```text
src/main/java/com/zading/todoapi/dto/TodoResponse.java
```

字段：

```java
private Long id;
private String title;
private boolean completed;
private LocalDateTime createdAt;
private LocalDateTime updatedAt;
```

为什么放在 `dto` 包？

因为它属于接口数据传输对象。

现在 `dto` 包里有三类对象：

```text
CreateTodoRequest   前端创建 Todo 时传入
UpdateTodoRequest   前端修改 Todo 时传入
TodoResponse        后端返回给前端
```

这就形成了请求/响应分离。

## 第十步：新增 TodoMapper

文件：

```text
src/main/java/com/zading/todoapi/mapper/TodoMapper.java
```

作用：

```text
Todo Entity -> TodoResponse DTO
```

核心代码：

```java
public TodoResponse toResponse(Todo todo) {
    return new TodoResponse(
            todo.getId(),
            todo.getTitle(),
            todo.isCompleted(),
            todo.getCreatedAt(),
            todo.getUpdatedAt()
    );
}
```

为什么不直接在 Controller 里 new？

因为转换逻辑以后可能变复杂。

比如：

- 时间格式转换
- 字段重命名
- 多个 Entity 拼成一个 Response
- 隐藏敏感字段

提前放进 Mapper，会让 Controller 更干净。

## 第十一步：Controller 返回 TodoResponse

文件：

```text
src/main/java/com/zading/todoapi/controller/TodoController.java
```

现在列表接口返回：

```java
public List<TodoResponse> getTodos(...)
```

详情接口返回：

```java
public TodoResponse getTodo(@PathVariable Long id)
```

创建接口返回：

```java
public ResponseEntity<TodoResponse> createTodo(...)
```

为什么 Service 还返回 Todo？

目前项目规模还小，Service 继续处理业务实体，Controller 通过 Mapper 转换成响应 DTO。

你现在先掌握这条边界：

```text
Repository / Service 内部使用 Entity
Controller 对外返回 DTO
```

后面项目更复杂时，可以再引入更细的 Application Service 或专门的 assembler。

## 第十二步：测试为什么要读取真实 id？

在讲 id 之前，先看测试配置也做了一次整理。

测试现在启用了：

```java
@ActiveProfiles("test")
```

并新增：

```text
src/test/resources/application-test.properties
```

为什么这样做？

- 默认环境使用 H2 文件数据库。
- `postgres` 环境以后连接 PostgreSQL。
- `test` 环境使用 H2 内存数据库。

这样测试不会污染你的本地开发数据，也不依赖你是否安装 PostgreSQL。

这就是配置分环境的真实用法：

```text
application.properties                 默认本地学习环境
application-postgres.properties        PostgreSQL 环境
src/test/resources/application-test.properties  自动化测试环境
```

之前测试里可能会假设：

```text
新建第一条 Todo 的 id 一定是 1
```

但数据库自增 ID 不一定每次都重置。尤其当测试共用同一个内存库时，下一条数据可能是 2、3、4。

所以测试改成：

```java
MvcResult result = mockMvc.perform(post("/api/todos")...)
        .andReturn();

Long todoId = readId(result);
```

然后用真实 id 去更新、删除：

```java
patch("/api/todos/{id}", todoId)
delete("/api/todos/{id}", todoId)
```

为什么这样更好？

因为真实业务里也不应该依赖“某条数据 id 一定是多少”。

测试应该验证行为，而不是依赖偶然的数据库状态。

## 本周复盘问题参考答案

### 1. 为什么不继续使用 `ddl-auto=update`？

`ddl-auto=update` 会让 Hibernate 根据 Entity 自动修改数据库表结构。

学习早期很方便，但真实项目里风险较高：

- 表结构变化没有明确历史。
- 团队成员的数据库状态可能不一致。
- 生产环境自动改表不可控。
- 很难清楚知道每次版本发布改了哪些数据库结构。

所以第六周改成：

```properties
spring.jpa.hibernate.ddl-auto=validate
```

含义是：

```text
Flyway 负责建表和改表
JPA 只负责校验 Entity 和表结构是否匹配
```

### 2. Flyway 的 `V1__create_todos_table.sql` 为什么不能随便改？

因为 Flyway migration 是数据库结构的历史记录。

当 `V1__create_todos_table.sql` 执行过之后，Flyway 会记录它的版本和校验值。

如果你之后修改这个文件，Flyway 会认为：

```text
已经执行过的历史脚本被篡改了
```

正确做法是新增脚本：

```text
V2__add_priority_to_todos.sql
V3__add_deleted_column_to_todos.sql
```

一句话：

```text
已经执行过的 migration 是历史，不是草稿。
```

### 3. `Todo` 和 `TodoResponse` 有什么区别？

`Todo` 是 Entity，负责数据库映射。

```text
Todo -> todos 表
```

`TodoResponse` 是 DTO，负责 API 响应。

```text
TodoResponse -> 返回给前端的 JSON 结构
```

它们现在字段看起来类似，但职责不同。

以后 `Todo` 可能增加内部字段，例如：

```java
private Long ownerId;
private boolean deleted;
private String internalNote;
```

这些字段不一定应该返回给前端。

所以：

```text
Entity 管数据库
DTO 管接口边界
```

### 4. 为什么创建时间、更新时间适合放在 Entity 生命周期方法里？

`createdAt` 和 `updatedAt` 是数据自身的生命周期信息。

使用：

```java
@PrePersist
void onCreate() {
    LocalDateTime now = LocalDateTime.now();
    this.createdAt = now;
    this.updatedAt = now;
}
```

可以在第一次保存前自动设置时间。

使用：

```java
@PreUpdate
void onUpdate() {
    this.updatedAt = LocalDateTime.now();
}
```

可以在更新前自动刷新 `updatedAt`。

这样比在每个 Service 方法里手动设置更不容易遗漏。

### 5. 为什么测试不应该假设新数据 id 一定是 1？

因为数据库自增 ID 不保证每次都从 1 开始。

可能出现：

- 前一个测试已经插入过数据。
- 数据删除了，但自增序列没有重置。
- 不同数据库的自增策略不同。
- 本地数据库已经有历史数据。

所以测试应该这样做：

```text
先创建 Todo
从响应里读取真实 id
再用这个 id 查询、修改、删除
```

测试应该验证业务行为，而不是依赖偶然的数据库状态。

## 更多复盘问题参考答案

### 1. `validate` 和 `update` 在 JPA 配置里有什么区别？

`update` 会尝试根据 Entity 自动更新数据库表结构。

`validate` 只校验 Entity 和数据库表是否匹配，不会改表。

第六周使用：

```properties
spring.jpa.hibernate.ddl-auto=validate
```

目的是让表结构变化交给 Flyway，而不是让 Hibernate 自动处理。

### 2. Flyway 如何知道哪些 migration 已经执行过？

Flyway 会在数据库里创建一张历史表，通常叫：

```text
flyway_schema_history
```

这张表记录：

- migration 版本
- 文件名
- 执行时间
- 校验值
- 是否成功

下次启动时，Flyway 会读取这张表，判断哪些脚本已经执行过，哪些还没执行。

### 3. 为什么新增字段应该写 `V2`，而不是修改 `V1`？

因为 `V1` 如果已经执行过，它就是数据库历史。

修改 `V1` 会导致 Flyway 校验失败。

正确做法是新增：

```text
V2__add_xxx_column.sql
```

这样数据库结构变化可以按版本追踪。

这就像 Git 提交历史：不要随便改已经共享出去的历史。

### 4. Mapper 的作用是什么？

Mapper 负责对象转换。

当前项目里主要是：

```text
Todo Entity -> TodoResponse DTO
```

把转换逻辑集中到 Mapper 后，Controller 就不需要到处 `new TodoResponse(...)`。

未来字段更多时，也更容易维护。

### 5. 为什么 Controller 返回 DTO，而 Service 仍然可以返回 Entity？

目前项目规模还小，Service 内部继续使用 Entity 可以保持业务逻辑简单。

Controller 是对外接口边界，所以在 Controller 层把 Entity 转成 DTO 返回。

当前边界是：

```text
内部业务层可以使用 Entity
对外 API 返回 DTO
```

后面项目更复杂时，可以进一步让 Service 直接返回 DTO 或应用层对象。

### 6. `createdAt` 为什么设置 `updatable = false`？

`createdAt` 表示创建时间，创建后不应该被更新。

配置：

```java
@Column(nullable = false, updatable = false)
private LocalDateTime createdAt;
```

表示 JPA 更新记录时不更新这个字段。

这样可以避免修改 Todo 时误改创建时间。

### 7. `test` profile 的价值是什么？

`test` profile 让测试环境拥有独立配置。

当前测试环境使用：

```text
H2 内存数据库
Flyway migration
ddl-auto=validate
```

好处是：

- 不依赖本地 PostgreSQL
- 不污染开发数据库
- 每次测试环境更可控
- 更接近真实启动流程
