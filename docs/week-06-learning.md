# 第六周学习说明：Profile + Flyway + DTO 分层

第六周的目标是把项目继续往真实后端工程推进。

第五周结束时，项目已经能做到：

```text
HTTP 请求
  -> Controller
  -> Service
  -> JpaRepository
  -> 数据库
```

第六周要解决三个更工程化的问题：

```text
1. 数据库表结构如何管理？
2. Entity 是否应该直接返回给前端？
3. 不同环境的配置如何长期维护？
```

本周完成后，当前项目变成：

```text
HTTP 请求
  -> Controller
  -> Service
  -> Repository
  -> 数据库

数据库结构
  -> 由 Flyway migration 管理

接口响应
  -> 返回 TodoResponse DTO
  -> 不直接暴露 Todo Entity
```

## 本周最终改动总览

| 改动 | 文件 | 目的 |
|---|---|---|
| 添加 Flyway 依赖 | `pom.xml` | 管理数据库结构版本 |
| 新增迁移脚本 | `db/migration/V1__create_todos_table.sql` | 用 SQL 明确创建表 |
| JPA 改为 validate | `application.properties` | 让 JPA 校验表结构，不自动改表 |
| 默认 H2 换成 v2 数据库文件 | `application.properties` | 避免旧数据库没有 Flyway 历史 |
| Postgres profile 启用 Flyway | `application-postgres.properties` | 以后 PostgreSQL 也走迁移 |
| Entity 增加时间字段 | `Todo.java` | 记录创建和更新时间 |
| 新增响应 DTO | `TodoResponse.java` | API 返回模型和数据库模型分离 |
| 新增 Mapper | `TodoMapper.java` | 集中处理 Entity -> DTO 转换 |
| Controller 返回 DTO | `TodoController.java` | 避免直接暴露 Entity |
| 新增测试 profile | `src/test/resources/application-test.properties` | 测试使用独立数据库配置 |
| 测试读取真实 id | `TodoApiApplicationTests.java` | 避免假设自增 id 一定是 1 |

## 第一步：为什么引入 Flyway？

第五周项目里有这样的配置：

```properties
spring.jpa.hibernate.ddl-auto=update
```

它的意思是：让 Hibernate 根据 Entity 自动更新数据库表。

学习早期这样很方便，但真实项目里有问题：

- 表结构变化没有清晰历史。
- 不容易知道某次上线改了哪些字段。
- 团队协作时，每个人数据库状态可能不一致。
- 自动改表不够可控，生产环境风险更高。

所以第六周改成：

```properties
spring.jpa.hibernate.ddl-auto=validate
```

含义变成：

```text
Flyway 负责建表和改表
JPA 负责校验 Entity 和数据库表是否匹配
```

这是一条很重要的后端工程边界。

## 第二步：添加 Flyway 依赖

文件：

```text
pom.xml
```

新增：

```xml
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-core</artifactId>
</dependency>

<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-database-postgresql</artifactId>
</dependency>
```

为什么要两个？

- `flyway-core` 是 Flyway 核心能力。
- `flyway-database-postgresql` 是 Flyway 对 PostgreSQL 的数据库支持。

你现在默认用 H2，未来启用 PostgreSQL profile 时也能直接使用 Flyway。

## 第三步：新增 V1 迁移脚本

文件：

```text
src/main/resources/db/migration/V1__create_todos_table.sql
```

内容：

```sql
CREATE TABLE todos (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title VARCHAR(255) NOT NULL,
    completed BOOLEAN NOT NULL DEFAULT FALSE,
    created_at TIMESTAMP NOT NULL,
    updated_at TIMESTAMP NOT NULL
);
```

Flyway 文件名有规则：

```text
V版本号__说明.sql
```

注意中间是两个下划线：

```text
V1__create_todos_table.sql
```

为什么要这样命名？

Flyway 会根据版本号顺序执行脚本：

```text
V1 -> V2 -> V3 -> ...
```

以后如果要新增字段，可以继续加：

```text
V2__add_priority_to_todos.sql
```

不要回头改已经执行过的 V1。这个习惯很重要。

## 第四步：配置 Flyway 和 ddl-auto=validate

默认配置：

```text
src/main/resources/application.properties
```

关键配置：

```properties
spring.jpa.hibernate.ddl-auto=validate
spring.flyway.enabled=true
spring.flyway.locations=classpath:db/migration
```

为什么这么做：

- `validate`：JPA 启动时检查 Entity 和数据库表是否匹配。
- `spring.flyway.enabled=true`：启动 Flyway。
- `locations`：告诉 Flyway 去哪里找 SQL 脚本。

启动顺序大致是：

```text
Spring Boot 启动
  -> 连接数据库
  -> Flyway 执行 migration
  -> Hibernate 校验 Entity 和表结构
  -> 应用启动完成
```

如果 migration 写错，项目会启动失败。

如果 Entity 和表结构不匹配，项目也会启动失败。

这听起来严格，但这是好事：问题越早暴露，越容易修。

## 第五步：为什么默认数据库文件改成 todo-db-v2？

默认配置里现在是：

```properties
spring.datasource.url=jdbc:h2:file:./data/todo-db-v2;MODE=PostgreSQL
```

为什么不是原来的 `todo-db`？

因为旧数据库可能是第五周由 Hibernate 自动建的，没有 Flyway 的版本记录。

第六周开始，数据库结构由 Flyway 接管。为了避免旧表和新迁移历史冲突，我们换了一个新的 H2 文件：

```text
data/todo-db-v2
```

这不会删除旧数据，只是默认使用新的学习数据库。

## 第六步：给 Todo 增加 createdAt / updatedAt

文件：

```text
src/main/java/com/zading/todoapi/model/Todo.java
```

新增字段：

```java
private LocalDateTime createdAt;

private LocalDateTime updatedAt;
```

为什么要加时间字段？

真实业务里几乎所有核心数据都需要知道：

- 什么时候创建的？
- 什么时候最后修改的？

这类字段常叫审计字段。

## 第七步：用 @PrePersist 和 @PreUpdate 自动维护时间

代码：

```java
@PrePersist
void onCreate() {
    LocalDateTime now = LocalDateTime.now();
    this.createdAt = now;
    this.updatedAt = now;
}

@PreUpdate
void onUpdate() {
    this.updatedAt = LocalDateTime.now();
}
```

含义：

- `@PrePersist`：第一次保存到数据库之前执行。
- `@PreUpdate`：更新数据库之前执行。

为什么不在 Service 里手动写？

因为创建时间、更新时间是 Entity 的生命周期逻辑。放在 Entity 里更集中，不容易漏。

这一步你可以这样理解：

```text
只要 Todo 被创建或更新，它自己知道如何维护时间字段。
```

## 第八步：为什么 Entity 不直接返回给前端？

第五周 Controller 直接返回：

```java
public Todo getTodo(@PathVariable Long id)
```

第六周改成：

```java
public TodoResponse getTodo(@PathVariable Long id)
```

原因是：

```text
Entity 是数据库模型
DTO 是接口模型
```

数据库模型经常会变化，比如以后可能增加：

```java
private String internalNote;
private boolean deleted;
private Long ownerId;
```

这些字段不一定应该返回给前端。

如果 Controller 直接返回 Entity，数据库字段变化就会影响 API 响应。

所以我们新增：

```text
TodoResponse
```

让 API 返回什么变得可控。

## 第九步：新增 TodoResponse

文件：

```text
src/main/java/com/zading/todoapi/dto/TodoResponse.java
```

字段：

```java
private Long id;
private String title;
private boolean completed;
private LocalDateTime createdAt;
private LocalDateTime updatedAt;
```

为什么放在 `dto` 包？

因为它属于接口数据传输对象。

现在 `dto` 包里有三类对象：

```text
CreateTodoRequest   前端创建 Todo 时传入
UpdateTodoRequest   前端修改 Todo 时传入
TodoResponse        后端返回给前端
```

这就形成了请求/响应分离。

## 第十步：新增 TodoMapper

文件：

```text
src/main/java/com/zading/todoapi/mapper/TodoMapper.java
```

作用：

```text
Todo Entity -> TodoResponse DTO
```

核心代码：

```java
public TodoResponse toResponse(Todo todo) {
    return new TodoResponse(
            todo.getId(),
            todo.getTitle(),
            todo.isCompleted(),
            todo.getCreatedAt(),
            todo.getUpdatedAt()
    );
}
```

为什么不直接在 Controller 里 new？

因为转换逻辑以后可能变复杂。

比如：

- 时间格式转换
- 字段重命名
- 多个 Entity 拼成一个 Response
- 隐藏敏感字段

提前放进 Mapper，会让 Controller 更干净。

## 第十一步：Controller 返回 TodoResponse

文件：

```text
src/main/java/com/zading/todoapi/controller/TodoController.java
```

现在列表接口返回：

```java
public List<TodoResponse> getTodos(...)
```

详情接口返回：

```java
public TodoResponse getTodo(@PathVariable Long id)
```

创建接口返回：

```java
public ResponseEntity<TodoResponse> createTodo(...)
```

为什么 Service 还返回 Todo？

目前项目规模还小，Service 继续处理业务实体，Controller 通过 Mapper 转换成响应 DTO。

你现在先掌握这条边界：

```text
Repository / Service 内部使用 Entity
Controller 对外返回 DTO
```

后面项目更复杂时，可以再引入更细的 Application Service 或专门的 assembler。

## 第十二步：测试为什么要读取真实 id？

在讲 id 之前，先看测试配置也做了一次整理。

测试现在启用了：

```java
@ActiveProfiles("test")
```

并新增：

```text
src/test/resources/application-test.properties
```

为什么这样做？

- 默认环境使用 H2 文件数据库。
- `postgres` 环境以后连接 PostgreSQL。
- `test` 环境使用 H2 内存数据库。

这样测试不会污染你的本地开发数据，也不依赖你是否安装 PostgreSQL。

这就是配置分环境的真实用法：

```text
application.properties                 默认本地学习环境
application-postgres.properties        PostgreSQL 环境
src/test/resources/application-test.properties  自动化测试环境
```

之前测试里可能会假设：

```text
新建第一条 Todo 的 id 一定是 1
```

但数据库自增 ID 不一定每次都重置。尤其当测试共用同一个内存库时，下一条数据可能是 2、3、4。

所以测试改成：

```java
MvcResult result = mockMvc.perform(post("/api/todos")...)
        .andReturn();

Long todoId = readId(result);
```

然后用真实 id 去更新、删除：

```java
patch("/api/todos/{id}", todoId)
delete("/api/todos/{id}", todoId)
```

为什么这样更好？

因为真实业务里也不应该依赖“某条数据 id 一定是多少”。

测试应该验证行为，而不是依赖偶然的数据库状态。

## 第十三步：当前运行方式

默认运行，使用 H2 文件数据库：

```bash
mvn spring-boot:run
```

默认数据库文件：

```text
data/todo-db-v2
```

启用 PostgreSQL：

```bash
DB_USERNAME=postgres DB_PASSWORD=你的密码 mvn spring-boot:run -Dspring-boot.run.profiles=postgres
```

运行测试：

```bash
mvn test
```

## 第十四步：你应该观察什么？

启动项目时，日志里会出现 Flyway 信息：

```text
Migrating schema "PUBLIC" to version "1 - create todos table"
```

这说明 Flyway 正在执行迁移脚本。

你也会看到 Hibernate 的 SQL：

```sql
insert into todos ...
select ... from todos ...
```

这说明 JPA 正在操作数据库。

## 第十五步：这一周你要真正理解的三句话

### 1. Flyway 管结构

```text
数据库表结构变化应该有版本记录。
```

### 2. JPA 管对象和查询

```text
Java Entity 和数据库表之间的映射由 JPA 处理。
```

### 3. DTO 管接口边界

```text
API 给前端什么，不应该完全由数据库表决定。
```
